# Agent 记忆能力规划方案

## 1. 背景

当前系统已经具备两类与记忆相关的基础能力：

- LangGraph `MemorySaver`，可在单次进程生命周期内保存会话状态
- `ChromaDB` 向量库，可保存和检索历史语义记忆

现阶段的主要问题不是“是否有记忆”，而是记忆能力不完整：

- 服务重启后，LangGraph 会话状态会丢失
- Agent 难以稳定检索“之前聊过的相关上下文”
- 长期记忆与当前线程状态之间没有清晰分层

因此，本次规划目标不是做一个复杂的通用记忆平台，而是先完成最实用的闭环：让 Agent 既能续接当前会话，又能检索历史相关对话。

## 2. 目标

本次规划采用方案 B：会话续接 + 历史语义检索。

具体目标如下：

- 同一个 `thread_id` 的会话在服务重启后仍可恢复
- Agent 在新一轮提问时，可以检索与当前问题最相关的历史上下文
- 当前线程上下文与跨线程历史记忆分层管理
- 方案尽量复用现有 `ChromaDB` 与 LangGraph 结构，避免引入过重的基础设施

## 3. 方案选择

### 3.1 为什么不只选 SQLite

只使用 SQLite 持久化 LangGraph checkpoint，可以解决“重启不丢上下文”，但无法很好解决“按语义回忆过去聊过什么”的问题。

SQLite 更适合：

- 保存完整状态
- 通过 `thread_id` 恢复上下文
- 提供审计和问题排查能力

SQLite 不擅长：

- 根据用户新问题做相似语义召回
- 从大量历史对话中找出最相关的片段

### 3.2 为什么不只选向量库

只使用向量库虽然能做语义检索，但不能可靠替代完整的会话状态存储。

向量库更适合：

- 检索相关历史经验
- 召回用户偏好、已确认事实、关键结论

向量库不适合：

- 保存 LangGraph 的完整执行状态
- 支持中断恢复和 `update_state`
- 精确还原一段会话执行现场

### 3.3 推荐方案

最适合当前项目的方案是：

- `SQLite` 负责短期记忆和会话续接
- `ChromaDB` 负责长期记忆和历史语义检索

这个方案同时覆盖“保存”和“检索”两类需求，复杂度也控制在当前项目可承受范围内。

## 4. 记忆分层设计

### 4.1 短期记忆

短期记忆指当前线程内的运行状态，包含：

- 最近多轮对话消息
- Agent 中间状态
- 工具执行结果
- 人机中断恢复所需状态

建议使用 SQLite 持久化 LangGraph checkpointer，实现：

- 同一 `thread_id` 下的会话恢复
- 服务重启后的上下文续接
- 调试时查看历史 checkpoint

### 4.2 长期记忆

长期记忆指可跨线程复用的历史知识，包含：

- 用户长期偏好
- 已经确认过的事实
- 过去任务的结论摘要
- 待延续事项

建议继续使用 `ChromaDB`，但写入内容从“整段对话”调整为“结构化摘要记忆块”。

## 5. 数据存储建议

### 5.1 SQLite 存储内容

SQLite 中只承担 LangGraph checkpoint 与线程状态持久化职责，核心信息包括：

- `thread_id`
- checkpoint 元数据
- State 快照
- 更新时间

这一层不负责语义检索，只负责保存完整上下文。

### 5.2 ChromaDB 存储内容

ChromaDB 中建议存储压缩后的“记忆块”，每条记忆块应尽量包含以下结构：

- 用户目标
- 用户偏好
- 关键事实
- 已完成结论
- 待继续事项

写入原则：

- 不要把每一句聊天都入库
- 不要把整段原始消息无差别做 embedding
- 优先写入对后续任务有复用价值的摘要

## 6. 运行时检索流程

每次收到用户新问题时，建议按以下顺序组装上下文：

1. 先读取当前 `thread_id` 的近期上下文
2. 再根据当前用户问题到 `ChromaDB` 检索 3 到 5 条相关历史记忆
3. 将“当前线程上下文 + 历史相关记忆”一起注入 Agent
4. 由 Agent 继续推理与执行

这样做的好处是：

- 先保证当前对话连续性
- 再补充跨会话的相关经验
- 避免把所有历史对话全部塞进 prompt

## 7. 记忆写入策略

建议不要每轮都立即写入长期记忆，而是按事件触发写入：

- 一轮任务明确完成后
- 用户明确表达长期偏好后
- 形成稳定分析结论后
- 会话结束或阶段性总结时

建议写入两类内容：

- 偏好类记忆：例如输出风格、关注重点、数据口径偏好
- 任务类记忆：例如某次分析的目标、结论与后续待办

## 8. 第一阶段落地范围

第一阶段只做最小可用闭环，不做过度扩展。

范围如下：

- 将 LangGraph 的内存 checkpointer 升级为 SQLite 持久化
- 继续使用现有 `ChromaDB` 作为长期记忆容器
- 优化长期记忆写入内容，改为摘要记忆块
- 在每轮提问开始时增加一次历史相关记忆检索

第一阶段暂不纳入：

- 超长对话摘要压缩
- 多层级记忆治理后台
- 用户可视化记忆管理界面
- 复杂的记忆评分和自动淘汰机制

## 9. 第二阶段演进方向

在第一阶段稳定后，可按需追加以下能力：

- 长对话摘要压缩，降低 token 压力
- 基于时间衰减或命中率的记忆清理策略
- 线程级“清除记忆”能力
- 记忆可视化查看与人工编辑
- 区分用户级记忆和任务级记忆

## 10. 风险与约束

- 如果长期记忆写得过于随意，检索结果会变脏，反而影响回答质量
- 如果每轮都做大量向量检索，会增加响应延迟
- 如果不区分“当前线程上下文”和“历史记忆”，prompt 会迅速膨胀
- 如果记忆摘要不结构化，后续很难稳定复用

## 11. 验收标准

完成第一阶段后，应满足以下结果：

- 服务重启后，同一 `thread_id` 能继续对话
- 用户提到“上次那个需求”时，Agent 能检索到相关历史记忆
- 当前线程上下文优先于历史记忆被使用
- 记忆检索结果数量可控，不明显拉长响应时间

## 12. 结论

对于当前项目，最合适的路径不是只做“会话持久化”，也不是只做“语义检索”，而是采用分层记忆方案：

- 用 SQLite 解决“不断线”
- 用 ChromaDB 解决“能回忆”

这是当前成本最低、收益最高、也最符合现有项目结构的实现方向。
